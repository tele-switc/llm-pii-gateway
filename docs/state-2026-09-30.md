## ③ 硬编码密钥扫描（只报字段名与位置，零明文）

**代码内硬编码 API key：未发现**。config.yaml 的三个 key 全部走环境变量引用：`api_key: os.environ/OPENROUTER_API_KEY`（config.yaml:23）、`os.environ/NVIDIA_API_KEY`（:34）、`master_key: os.environ/LITELLM_MASTER_KEY`（:46）。✅

**明文密钥文件（落盘在仓库目录内，风险点）**：
| 文件 | 性质 | 来源代码 |
|---|---|---|
| `vault/vault.key`（44 字节） | Fernet 密钥文件（自动生成） | vault.py:22 默认路径 KEY_PATH=vault/vault.key；:26-37 无 env 时自动生成 0600（Windows 权限位实际不生效 [C]） |
| `.vaulttest/key`、`.vault_test/key`、`.vault_test2/key`（各 44 字节） | 测试用密钥文件 | 测试脚本生成（drill.py:22 会指向真 vault key） |
| `vault/*.enc`、`.vaulttest/*.enc` 等 | 加密映射条目 | 无 gc 调用 → 永不过期清理（见②） |

处置建议：密钥文件**不在代码里**，但与数据同目录同备份，违反 vault.py:5 自己的"不与 vault 同备份"原则；且该目录不是 git 仓，无历史泄漏面，当前风险=本机文件系统级。建议：VAULT_KEY 走环境变量（vault.py:27-28 已支持），把 *.key 移出仓库目录并全目录加进备份排除。

## ⑤ 下一步唯一动作建议

**把 vault 的 TTL 闭环补上（调用 gc）**：在 pii_guardrail 入口每次请求时顺手 `vault.gc()`（一行，pii_guardrail.py:120 函数体内加），或在 drill/watchdog 里挂周期调用。理由：这是全仓唯一"文档声称了、代码也写了、但没人执行"的控制点（TTL/保留期），它直接决定"映射表泄露则脱敏全部作废"（vault.py:4）这条最坏假设的暴露窗口——当前窗口是**无限期**；相比之下 user 字段姓名检测（红测试）与 provider 审计修正都是已知缺口的有意取舍，且都有 ZDR-only deny 兜底，而 TTL 缺失没有任何兜底层。
